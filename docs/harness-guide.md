# 하네스 가이드 — 리드가 신규 입사자에게

> 이 문서는 미리디 블로그 「AI Agent로 테스트 커버리지 100% 달성한 실전 전략」(2026-04)에 공개된 방식을
> 이 데모 프로젝트 규모에 맞춰 옮긴 것이다. 미리디 내부 자료가 아니라 공개 글에서 출발한 해석이다.

## 0. 먼저 알아야 할 한 문장

**AI 가 실수하지 않게 만드는 게 아니라, 실수가 드러나는 구조를 만든다.**

AI 는 빠르게 많이 쓴다. 대신 같은 요청에도 결과가 들쭉날쭉하고, 실행하지 않은 빌드를 성공했다고 말하기도 한다.
그래서 우리는 프롬프트를 잘 쓰는 데 힘을 쓰지 않고, 아래 세 가지를 시스템으로 만든다.

| 문제 | 장치 | 이 레포에서 |
|---|---|---|
| 요청마다 결과가 다르다 | 절차를 고정한 스킬 | `.claude/skills/*` |
| "완료했습니다"를 믿을 수 없다 | 숫자로만 보고, 숫자는 도구가 뽑는다 | `coverage.py`, `./gradlew build` |
| AI 는 정책이 맞는지 모른다 | 사람은 테스트의 **의미**만 본다 | 사이클 6단계 |

## 1. 개발 사이클 (기능 하나)

| # | 단계 | 누가 | 무엇으로 | 산출물 |
|---|---|---|---|---|
| 1 | 스펙 정리 | 나 | `docs/specs/_template.md` | 스펙 .md (케이스 목록이 핵심) |
| 2 | 태스크 분할 | 나 | `TASKS.md` | 유스케이스·어댑터 단위 태스크 |
| 3 | 구현 | AI | `/implement T-xxx` | 코드, 마이그레이션 |
| 4 | 유닛 테스트 | AI | (implement 안에서 unit-test 절차) | 테스트 |
| 5 | 커버리지 수치 검증 | 도구 → AI 반복 | `./gradlew test`, `coverage.py` | 100% 또는 미달 사유 |
| 6 | **테스트 의미 리뷰** | **나** | implement 보고의 "스펙 대조표" | 승인 또는 수정 지시 |
| 7 | 통합 테스트 | AI | `/integration-test T-xxx` | Testcontainers 테스트 |
| 8 | 분리된 리뷰 | AI(별도 컨텍스트) | `reviewer` 에이전트 | 차단/권장/참고 목록 |

마지막에 `./gradlew build` 가 통과하면 `TASKS.md` 를 `DONE` 으로 바꾸고 커밋한다. `DONE` 은 사람만 찍는다.

### 6단계에서 사람이 하는 일
리드로서 가장 강조하는 단계다. 커버리지 100%는 "모든 줄이 실행됐다"는 뜻이지 "정책이 맞다"는 뜻이 아니다.
블로그 글에서도 AI 가 "페이지가 없는 디자인이 정상 업로드된다"는 테스트를 만들었다 — 커버리지상 문제없지만 정책상 틀렸다.

스펙 대조표에서 이것만 확인한다.
1. 스펙 케이스마다 테스트가 있는가
2. 스펙에 없는 테스트가 있다면, 그건 스펙 누락인가 잘못된 동작인가
3. "발견 사항"의 버그 후보를 어떻게 처리할지 결정

## 2. 구성 요소와 만든 이유

### 빌드 (`build.gradle.kts`)
- **`test` 와 `integrationTest` 분리**: AI 가 반복하는 4~5단계 루프는 빨라야 한다. Docker 를 띄우는 테스트가 섞이면 한 바퀴가 수십 초 늘어나고, 토큰과 집중력이 같이 샌다. 커버리지 게이트도 유닛 테스트 기준이다(블로그와 같음).
- **측정 범위를 `domain`, `application/service`, `adapter/in/web` 로 한정**: 비즈니스 로직이 사는 곳만 100%를 요구한다. 설정 클래스나 영속성 어댑터에 100%를 걸면 의미 없는 테스트가 늘어난다.
- **`jacocoTestCoverageVerification` 을 `check` 에 연결**: push Hook 을 쓰지 않는 대신, `./gradlew build` 자체가 기준 미달이면 실패한다. "빌드 성공 = 기준 통과"라서 AI 의 보고를 믿을 필요가 없다.
- **ArchUnit**: 커버리지가 "충분히 테스트했나"를 지킨다면, ArchUnit 은 "경계를 지켰나"를 지킨다. AI 는 한 번에 여러 파일을 고치다 domain 에 JPA 를 끌어들이기 쉽다.

### 커버리지 스크립트 (`.claude/scripts/coverage.py`)
- AI 에게 HTML 리포트를 읽히지 않는다. 해석의 여지가 생기고 토큰도 많이 든다.
- 스크립트가 XML 을 읽어 **파일별 수치, 미커버 라인 번호, 일부만 커버된 분기 라인**만 표로 낸다. 종료 코드(0/1/2)로 판정한다.
- 블로그의 "측정은 전문 도구가, 작성만 AI 가"를 코드로 옮긴 것이다.

### CLAUDE.md
- 모든 세션에 자동으로 실린다. 그래서 **짧게**, 지도 역할만 한다. 상세는 `docs/conventions/` 로 연결.
- "반드시 지킬 것"에는 실제로 사고가 났던 유형만 둔다: 실행 안 하고 보고, 기대값 바꿔서 통과, 범위 이탈.

### 스킬 (`.claude/skills/`)
모든 스킬은 같은 골격이다: **입력 → 먼저 읽을 것 → 절차(생략 금지) → 완료 기준(수치) → 보고 형식 → 금지.**
- `implement`: 3~5단계 + 6단계 자료(스펙 대조표) 준비. 4~5단계는 `unit-test` 절차를 그대로 호출해 규칙을 한 곳에서 관리한다.
- `unit-test`: 반복은 최대 3회. 무한 루프로 토큰을 태우는 것보다 "여기까지 했고 이 줄은 이래서 못 덮었다"는 보고가 낫다.
- `integration-test`: Docker 가 없으면 실행한 척하지 말고 멈춘다.

스킬에 **"프로덕션 코드를 고치지 말고 발견 사항으로 보고"**를 넣은 이유: 테스트를 쓰다 버그를 찾으면 AI 는 코드를 고쳐서 테스트를 통과시키려 한다. 그 순간 버그 수정과 정책 결정이 사람 모르게 일어난다.

### 리뷰 에이전트 (`.claude/agents/reviewer.md`)
스킬이 아니라 서브에이전트로 만든 이유는 **컨텍스트 분리**다. 구현한 세션이 자기 코드를 리뷰하면 자기가 내린 판단을 다시 정당화한다. 리뷰어는 파일 수정 권한 없이 읽고 보고만 한다.

### 권한 (`.claude/settings.json`)
- 반복 실행할 명령(`./gradlew`, `coverage.py`)은 허용해 매번 승인 누르는 피로를 없앤다.
- `git push`, `rm -rf`, `.env` 읽기는 막는다. 배포를 하지 않는 프로젝트라 push 는 사람이 직접 한다.

## 3. 첫 주에 할 일: 시험 운전 (T-000)

하네스는 만들었을 때가 아니라 **한 번 돌려 봤을 때** 완성된다.

1. 아주 작은 더미 기능을 정한다 (예: 닉네임 정책 검증 — 2~12자, 공백 불가).
2. 스펙을 템플릿으로 쓰고 `TASKS.md` 에 넣는다.
3. `/implement` 를 실행한다. **같은 태스크를 새 세션에서 한 번 더** 실행해 결과를 비교한다.
4. 다음을 기록한다.
   - AI 가 건너뛴 절차가 있었나 → 해당 스킬의 절차에 명시
   - 실행하지 않은 수치를 보고했나 → 금지 항목 강화
   - 스펙 대조표로 6단계 리뷰가 쉬웠나 → 보고 형식 조정
5. 보정 내용은 ADR 로 남긴다. 하네스도 코드처럼 리뷰받고 버전 관리된다.

## 4. 하네스를 고칠 때의 규칙
- 사고가 한 번 나면 기록, 두 번 나면 스킬에 반영한다.
- 규칙은 추가만 하지 말고 지운다. 스킬이 길어질수록 AI 는 뒤쪽 규칙을 놓친다.
- 아키텍처 규칙(ArchUnit)과 커버리지 기준은 ADR 없이 바꾸지 않는다.
