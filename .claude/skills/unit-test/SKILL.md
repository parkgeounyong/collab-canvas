# unit-test

개발 사이클 4~5단계(유닛 테스트 작성 → 커버리지 수치 검증)를 수행한다.

## 입력
- `TASKS.md` 의 태스크 ID, 또는 대상 클래스 이름 목록

## 먼저 읽을 것
- `docs/conventions/testing.md`
- 태스크에 연결된 `docs/specs/*.md` 의 **5. 케이스 목록**

## 절차 (순서대로, 생략 금지)

1. **대상 확정**
   대상 클래스가 `domain`, `application/service`, `adapter/in/web` 중 하나인지 확인한다.
   `adapter/out`, `adapter/in/websocket` 이면 이 스킬을 중단하고 `integration-test` 스킬을 쓰라고 보고한다.

2. **시작 수치 기록**
   `./gradlew test` 실행 후 `python3 .claude/scripts/coverage.py {클래스명}` 을 실행하고 출력을 그대로 기록한다.

3. **스펙 케이스 → 테스트 작성**
   스펙의 케이스 목록을 하나씩 테스트로 옮긴다. `@DisplayName` 은 케이스 문장과 일치시킨다.
   작성 중 코드가 스펙과 **다르게** 동작한다는 걸 알게 되면, 그 동작을 성공으로 기대하는 테스트를 쓰지 말고 발견 사항에 적는다.

4. **실행**
   `./gradlew test` 를 실행한다. 실패하면 원인을 분류한다.
   - 테스트 작성 실수 → 테스트를 고친다.
   - 프로덕션 코드가 스펙과 다름 → 코드는 고치지 않는다. 발견 사항에 적고 해당 테스트는 제외한다.

5. **측정**
   `python3 .claude/scripts/coverage.py {클래스명}` 을 실행한다.
   - 종료 코드 0 → 7단계로.
   - FAIL → 출력된 미커버 라인·일부 분기 라인을 읽고 6단계로.

6. **분기 보강**
   미커버 라인마다 "어떤 입력이면 이 줄에 도달하는가"를 찾아 테스트를 추가한다. 이 테스트의 `@DisplayName` 이 스펙에 없는 정책을 말하게 된다면, 스펙 누락으로 발견 사항에 적는다.
   도달할 수 없는 코드(방어 코드, 죽은 분기)라고 판단되면 억지로 테스트하지 말고 근거와 함께 보고한다.
   4단계로 돌아간다. **4~6단계는 최대 3회** 반복하고, 그래도 미달이면 남은 라인과 이유를 보고하고 멈춘다.

7. **보고** (아래 형식)

## 완료 기준
- `./gradlew test` 성공
- `python3 .claude/scripts/coverage.py {대상}` 종료 코드 0
두 명령을 **이번 작업에서 실제로 실행한 출력**이 있어야 완료라고 말할 수 있다.

## 보고 형식
```
### unit-test 보고: {태스크 ID}
#### 커버리지 (coverage.py 출력 그대로)
- 시작: {표}
- 종료: {표}

#### 작성한 테스트
| DisplayName | 근거 (스펙 케이스 # / 분기 보강) |
|---|---|

#### 발견 사항
- [버그 후보] {파일:라인} {스펙과 다른 동작}
- [스펙 누락] {코드에는 있지만 스펙에 없는 정책}
- [도달 불가] {파일:라인} {이유}
(없으면 "없음")
```

## 금지
- 명령을 실행하지 않고 수치나 성공을 보고하기
- 기존 테스트의 기대값 변경
- 프로덕션 코드 수정 (발견 사항으로만 보고)
- `@Disabled`, 검증 없는 테스트, 리플렉션
- 대상 외 클래스의 테스트 작성
